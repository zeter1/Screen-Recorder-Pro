# 05. Потоки, Tkinter и дочерние процессы

## Главное правило Tkinter

Tkinter не является thread-safe.

Только GUI-поток может:

- читать и менять виджеты;
- вызывать `winfo_*`, `update`, `update_idletasks`;
- читать `StringVar`, `BooleanVar`, `IntVar`;
- показывать `messagebox`;
- создавать/закрывать окна.

Фоновый поток должен вернуть результат через:

```python
self.root.after(0, callback)
```

или через очередь, которую читает GUI-поток.

Это правило относится и к диагностике. Фоновые потоки трея, горячей клавиши,
preflight и FFmpeg не должны читать `problem_logs_*_var`. Для лимита и настроек
логов они используют обычный словарь `self.settings`, синхронизируемый GUI-потоком.
Иначе возможна взаимная блокировка: поток держит файловый lock и ждёт Tkinter,
а GUI одновременно ждёт тот же файловый lock.

## Почему это критично в этом проекте

Ранее обращения к Tkinter из потока захвата или остановки приводили к:

- `Python не отвечает`;
- зависанию при старте/стопе из плавающей панели;
- незавершённому FFmpeg trailer;
- оставшимся `ffmpeg.exe`;
- заблокированным папкам.

## Runtime-снимки настроек

Перед стартом записи значения Tkinter копируются в обычные поля, например:

```text
recording_requested_fps
recording_effective_fps
recording_refresh_hz
recording_cursor_visible
recording_cursor_size_percent
recording_cursor_highlight
recording_cursor_highlight_size
recording_settings_snapshot
```

Фоновые потоки должны использовать эти поля, а не Tkinter-переменные.

## Managed subprocess

Основной API:

```python
self.start_managed_process(command, ...)
self.run_managed_process(command, ...)
self.register_child_process(process)
self.unregister_child_process(process)
self.terminate_process_tree(process, ...)
```

Он обеспечивает:

- единую рабочую папку;
- регистрацию дочерних процессов;
- диагностические события старта/завершения;
- ожидаемые return codes;
- принудительную очистку при выходе.

## Почему нельзя голый `Popen`

Незарегистрированный процесс:

- не попадёт в `child_processes`;
- может пережить закрытие GUI;
- может держать папку или файл;
- не попадёт в централизованные логи;
- усложнит диагностику return code и времени работы.

Исключение допустимо только при обосновании и собственной гарантии регистрации/закрытия, но предпочтительно расширить managed API.

## Watchdog записи

`ProcessMixin` периодически проверяет активный FFmpeg.

Если процесс неожиданно завершён:

1. фиксируется причина;
2. событие пишется как ERROR;
3. пользователь получает статус;
4. вызывается обычный путь остановки;
5. программа пытается сохранить доступную корректную часть записи.

Не заменяй watchdog агрессивным polling в коротком цикле.

Живой процесс ещё не доказывает, что видео продолжается: микрофон может поддерживать
рост `out_time` после остановки Desktop Duplication. Поэтому watchdog отдельно следит за
ростом `frame` в progress. Дополнительно stderr FFmpeg непрерывно дренируется отдельным
потоком. Этот поток не вызывает `root.after()` и не трогает Tkinter: при
`DXGI_ERROR_ACCESS_LOST` он передаёт неизменяемый сигнал через ограниченную очередь.

Главный Tk-поток сверяет session/segment/process generation/PID, ждёт возврата входного
desktop `Default` и только после этого запускает штатный rollover сегмента. Результат
фонового stop-worker также возвращается через очередь, которую опрашивает Tk-поток.
Устаревший сигнал не может перезапустить новую запись.

Если ddagrab не дал первый кадр за 12 секунд или счётчик не менялся 6 секунд без
явного DXGI-маркера, остаётся резервный progress-watchdog. После трёх последовательных
неудачных восстановлений обычный путь остановки сохраняет доступные сегменты. Счётчик
попыток сбрасывается после трёх секунд здорового нового сегмента, поэтому отдельные
переходы `Ctrl+Alt+Delete` в длинной записи не суммируются как один бесконечный сбой.

## Правильная остановка

Живой фильтр не должен генерировать бесконечный хвост после EOF: `tpad:stop=-1`
в v25 мешал `q` завершить FFmpeg и приводил к принудительному завершению через
12 секунд. Особенно короткий fragmented MP4 мог остаться размером 28 байт без
`moov`. Увеличение timeout не исправляет эту причину. В v26 конечный stop-frame
создаётся из закрытого файла в потоке финализации; `q` снова завершает захват.

Остановка программы во время записи не должна мгновенно убивать FFmpeg и оставлять обычное имя повреждённого MP4.

`LifecycleMixin.exit_app()`:

- откладывает выход при старте/паузе/finalize;
- сначала сохраняет активную запись;
- останавливает аудиометры;
- закрывает overlay и webcam;
- удаляет hotkeys;
- завершает процессы;
- останавливает tray;
- уничтожает root.

Не обходи этот путь через прямой `root.destroy()`.

## Долгие операции

В фоновом потоке должны выполняться:

- запуск/остановка тяжёлого FFmpeg;
- merge/finalize;
- ffprobe больших файлов;
- анализ кадров;
- экспорт GIF;
- обрезка;
- `taskkill` и ожидание процессов;
- тяжёлое сканирование логов.

GUI должен обновлять статус и блокировать конфликтующие кнопки.

## Тайм-ауты

Для subprocess обязательно выбирать разумный тайм-аут по типу операции:

- probe устройств: секунды;
- ffprobe: десятки секунд;
- завершение процесса: 0.5–3 секунды с escalation;
- merge/encode: минуты;
- длинный экспорт: до десятков минут, но не бесконечно.

После timeout:

1. записать контекст;
2. завершить дерево процессов;
3. сохранить stderr;
4. не удалять полезные temp-файлы до диагностики.

## Проверка после изменений потоков

- GUI реагирует во время запуска и сохранения;
- двойной клик Start не создаёт второй процесс;
- Stop во время запуска обрабатывается безопасно;
- Exit во время записи сначала сохраняет файл;
- pause/resume не запускаются параллельно;
- после полного выхода нет лишних FFmpeg;
- traceback фонового потока попадает в логи.
