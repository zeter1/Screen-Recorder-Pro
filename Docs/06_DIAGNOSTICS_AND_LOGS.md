# 06. Диагностика и логи проблем

## Назначение

Логи должны позволить определить причину без догадок и без повторного воспроизведения бага.

Каждая запись создаёт отдельную папку в `Логи проблем`, если функция включена.

## Глобальные диагностические логи

В корне `Логи проблем` могут находиться:

```text
diagnostic_<timestamp>_pid<pid>.txt
diagnostic_latest.txt
```

Они нужны для проблем запуска, интерфейса, настроек и процессов до создания папки записи.

## Диагностика горячей клавиши и скриншота

Для проверки скриншота сопоставляй события по порядку:

1. `native_screenshot_hotkey_ready` — Windows подтвердил `RegisterHotKey`, записан `thread_id`;
2. `hotkey_registration_success` — выбран backend и зафиксировано состояние потока;
3. `hotkey_callback_received` — Windows действительно передал нажатие;
4. `screenshot_requested` — действие дошло до GUI-потока;
5. `screenshot_snapshot_started` — начато сохранение экрана до потери фокуса;
6. `screenshot_snapshot_ready` — сохранены размер кадра, время и масштаб координат;
7. `capture_region_selector_opened` — полноэкранное окно показывает сохранённый кадр;
8. `screenshot_annotation_tool_selected` — выбран собственный инструмент скриншота и видимость палитры;
9. `screenshot_annotation_color_selected` — цвет изменён без закрытия активной палитры;
10. `screenshot_annotation_size_selected` — изменена толщина карандаша или размер стрелки;
11. `screenshot_annotation_toolbar_moved` — сохранена новая глобальная позиция панели;
12. `screenshot_annotation_added`, `screenshot_annotation_undone` или
   `screenshot_annotations_cleared` — изменение пометок с их количеством;
13. `capture_region_selection_started` — мышь нажата в режиме `Область`;
14. `capture_region_selection_finished` — записаны статус, координаты, размеры, время, цвета и сводка пометок;
15. `screenshot_copied_to_clipboard` — пометки нанесены, область вырезана и помещена в буфер.

Статус `too_small` означает область меньше 16×16 пикселей, `escape` — явную отмену,
`selector_error` — исключение окна выбора. `screenshot_request_ignored` объясняет повторное
нажатие во время уже выполняющегося снимка. Поэтому отсутствие файла или события больше
не нужно трактовать по догадке.

Для `Print Screen` на Windows нормальный `screenshot_backend` — `windows_register_hotkey`.
`native_screenshot_hotkey_failed` содержит код и текст ошибки WinAPI, например конфликт с
другой программой. `native_screenshot_hotkey_stop_result.thread_alive_after_join=false`
подтверждает, что при восстановлении после автозапуска прежний поток действительно закрыт.
Значение `keyboard_fallback` означает, что WinAPI-регистрация не удалась и временно используется
старый backend. Если нет `hotkey_callback_received`, сначала проверь события backend, а не захват экрана.

`screenshot_snapshot_failed` содержит исключение подготовки кадра. Поля
`size_matches_virtual_screen` и `coordinate_scale` позволяют отличить ошибку DPI/геометрии
от закрытия временной панели. Для исправного нового контура у
`capture_region_selector_opened.background_mode` должно быть значение
`frozen_snapshot_before_selector_focus`, а у итогового события — такой же источник кадра.
Для новой панели ожидаются `annotation_tools_enabled=true`,
`annotation_backend=screenshot_canvas_v3` и
`color_palette_behavior=persistent_below_active_draw_or_arrow_tool`. Поля `annotation_count`
`annotation_colors` и `annotation_sizes` итогового события показывают число пометок, реально
использованные цвета и размеры. `toolbar_position_source=settings` подтверждает восстановление
позиции после запуска. Сами длинные списки точек в лог не записываются.

## Как читать логи рывков

Рекомендуемый порядок:

1. `00` — итог и версия сборки;
2. `04` — исключения и технические предупреждения;
3. `06` — агрегированная сводка;
4. `13` — реальная длительность и drift;
5. `14` — детальный timing/PTS/DTS, если короткой сводки недостаточно;
6. `02` — точная команда FFmpeg;
7. `07` — progress/stall/dup/drop;
8. `08` — нагрузка;
9. `09` и `10` — содержимое кадров;
10. `11_версия_исходников.json` — точный отпечаток версии; snapshot кода читать только если он появился из-за ошибки.

## Уровни причин рывков

Разделяй минимум четыре уровня:

1. **Захват** — Desktop Duplication не получил новое состояние экрана.
2. **Кодирование** — NVENC/CPU не успевал принимать кадры.
3. **Таймлайн/контейнер** — PTS/DTS, CFR, gaps, drift.
4. **Воспроизведение** — плеер, декодер, VSync, частота монитора.

## Что является сильным доказательством

- `Non-monotonic DTS`;
- обратные или одинаковые PTS в движении;
- много нулевых/очень коротких интервалов;
- серьёзные packet gaps;
- `speed` стабильно ниже реального времени;
- остановки роста `out_time`;
- рост `drop`;
- длительная перегрузка CPU/GPU/NVENC;
- активный swap I/O в момент проблемы;
- drift, растущий с длительностью;
- совпадение визуального кандидата с техническим событием.

## Что не является доказательством само по себе

- высокий процент одинаковых кадров на статичном рабочем столе;
- анимация приложения с 30 FPS внутри файла 72 FPS;
- один длинный первый интервал;
- `dup/drop=0` при визуальных повторах;
- ровные PTS;
- субъективное ощущение без контроля в другом плеере;
- единичный пик CPU без ухудшения progress.

## Правила записи ошибок

При исключении сохраняй:

```text
контекст операции
тип исключения
сообщение
полный traceback
ключевые пути
команду subprocess
return code
последний значимый stderr
состояние записи
```

Не перехватывай исключение пустым `except Exception: pass`, если оно влияет на пользовательский результат. Допустимый best-effort код должен оставлять диагностическое событие хотя бы уровня WARN.

## Ограничение размера

Логи имеют лимиты и автоочистку. При добавлении нового потока данных:

- используй JSONL для последовательных samples;
- ограничивай частоту адаптивно: подробно на старте/аномалии, реже в штатной работе;
- ограничивай размер файла;
- не дублируй одинаковые строки;
- сохраняй агрегированную статистику до удаления подробностей;
- при достижении лимита потокового лога сохраняй начало и свежий хвост, а не теряй конец записи.

Обычные и ошибочные логи по умолчанию хранятся 120 дней. Автоматическая и ручная очистка
старых логов обрабатывает только распознанные папки сессий и файлы `diagnostic_*.txt`,
созданные Screen Recorder Pro. Посторонние файлы и папки внутри `Логи проблем` пропускаются
и перечисляются в `cleanup_problem_logs_finish` как `skipped_unrecognized_names`.
Кнопка явного удаления всех логов остаётся отдельным подтверждаемым пользователем действием.

## Пост-анализ после сохранения

Тяжёлый анализ содержимого кадров (`09`/`10`) не должен задерживать готовый файл и UI.
Сначала выполняются остановка, сборка, `ffprobe`/тайминг и проверка результата. После этого
пользователь получает сохранённое видео, а визуальный анализ идёт в фоновом потоке.

Если начинается новая запись или программа закрывается, фоновый визуальный анализ отменяется,
чтобы его FFmpeg не конкурировал с основной записью за GPU, диск и декодер.

## Известная тонкость

Первичный placeholder в `06_...json` создаётся до завершения записи. Источником истины после сохранения являются финальный отчёт, точная FFmpeg-команда и `13_...json`. Не делай вывод только по полю placeholder, если оно ещё имеет статус `recording_in_progress`.
